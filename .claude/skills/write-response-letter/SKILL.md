# Write Response Letter

Work on one explicitly scoped comment or a small set of closely related comments at a time, but never work from those comments alone. Read the full project first, preserve a project-level revision strategy, and draft each response in light of the manuscript's theory, evidence, other reviews, and editor priorities.

The default deliverable is the response unit or units for the user's stated scope, not a complete response letter. Keep separate comment numbers and separate local answers even when several comments share one theoretical or empirical foundation. Draft a full opening, reviewer section, or complete package only when the user explicitly asks for it. Never generate responses outside the requested scope merely because the full set of reviews is available.

## Non-negotiable rules

1. Read [references/full-project-and-strategy.md](references/full-project-and-strategy.md) completely before drafting the first response for a project.
2. Read the editor's letter, all reviewer reports, original and revised manuscripts, relevant analyses, supplements, and study materials before treating any response as evidence-grounded.
3. Build and retain a full-project issue map. Use it to interpret each individual comment and prevent contradictions across responses.
4. Follow the current decision letter first, then the target journal's current instructions, then this skill. Do not use preset journal modes.
5. Identify both the explicit request and the likely underlying concern. Treat the latter as a planning hypothesis, never as a claim about the reviewer's motives.
6. Never invent a definition, theoretical rationale, author intention, revision, analysis, result, page number, citation, or journal rule. Use a visible `AUTHOR INPUT REQUIRED` placeholder for missing information.
7. Use the shortest response that fully resolves the concern. Do not force every response through every element of a fixed architecture.
8. Revise the manuscript when a careful reader's misunderstanding exposes ambiguity. Do not rely on the response alone to repair unclear theory, methods, or results.
9. Make every consequential claim verifiable in the manuscript, analysis output, table, figure, appendix, supplement, or author-confirmed revision plan.
10. When the user selects several comments, accept the scope only when the comments are closely related enough to share a coherent conceptual, empirical, or revision foundation. Preserve each comment's numbering and answer it locally rather than merging distinct requests into one omnibus response.

## Workflow

### 1. Build the full-project picture

Read the complete project materials listed in [references/full-project-and-strategy.md](references/full-project-and-strategy.md). Identify the manuscript's central contribution, construct system, causal or explanatory logic, study package, evidence strengths and limits, terminology, current revisions, and unresolved author decisions.

Do not draft from reviewer comments alone. If required project files are unavailable, state what is missing and limit the response to a provisional strategy or placeholder-bearing draft.

### 2. Build the revision context memo

Create an internal memo that records:

- editor priorities and decision-critical concerns;
- overarching themes across reviews;
- explicit and likely underlying concerns;
- overlapping and conflicting requests;
- approved conceptual and empirical revision strategy;
- canonical terminology;
- verified analyses and findings;
- manuscript, table, figure, appendix, and supplement locations;
- unresolved facts, author decisions, and placeholders.

Update this memo as each comment is resolved. Do not let one locally convenient response contradict the project's global strategy.

### 3. Select and diagnose the current response scope

Identify the exact comment or small set of closely related comments requested by the user. Preserve every comment and its numbering. Split comments into subquestions when necessary. Do not add unrelated comments to the drafting scope.

For each selected comment, record:

- the direct question or request;
- the likely uncertainty motivating it;
- its relationship to editor priorities and other reviews;
- its importance and complexity;
- the response decision;
- the required manuscript and analytic actions;
- the evidence available to support the response;
- any missing author input.

Choose among: accept and revise; partially accept; clarify and revise; add evidence; conduct an analysis; narrow or recalibrate a claim; specify a boundary condition; correct a misunderstanding through manuscript revision; respectfully disagree; or explain infeasibility and provide a compensating action.

### 4. Revise and verify before claiming

Confirm that every stated action exists or is an explicitly approved revision plan. Verify definitions, theoretical rationales, model specifications, samples, measures, controls, statistics, interpretations, terminology, and locations.

Write only verified facts into a submission-ready response. A plausible inference may guide a question to the author, but it may not become author prose without support.

### 5. Draft each minimum-sufficient response

Use the depth gate in [references/response-architecture.md](references/response-architecture.md):

- keep minor, fully resolved comments to one or two sentences;
- give substantive but straightforward comments only the reasoning and evidence they need;
- use the fuller architecture for decision-critical, contested, multi-part, infeasible, claim-changing, or evidence-intensive concerns.

Lead each response with the direct answer. Include appreciation only when useful. Use the reviewer's accurate terminology. Explain what changed and where. When selected comments overlap, identify one primary response for the shared reasoning and use precise cross-references in the others, but still give every comment a direct local answer.

### 6. Audit every response unit

Check that the response:

- answers every subquestion and begins with a direct answer;
- addresses the theoretical concern before adding analysis when theory is at issue;
- distinguishes theory, evidence, and interpretation;
- reports null or unfavorable evidence honestly;
- neither overstates the change nor understates remaining limitations;
- explains or makes evident how the revision improves the paper;
- uses precise, active, consistent, non-defensive language;
- contains no invented facts or unresolved hidden gaps;
- fits the full-project strategy and does not conflict with another response.

### 7. Return a focused deliverable

Unless the user asks for more, return:

1. **Draft response(s):** polished, separately numbered response units for only the requested comment or comments, each at the appropriate depth.
2. **Concern and strategy notes:** explicit concern, likely underlying concern, relationship to the full-project strategy, and recommended response decision.
3. **Manuscript actions:** exact changes and locations to verify or complete.
4. **Unresolved inputs:** visible placeholders, missing evidence, and author decisions.

Keep the author-ready prose first and the diagnostic notes secondary. Do not generate unrelated reviewer responses, a complete reviewer section, or a complete letter by default.
